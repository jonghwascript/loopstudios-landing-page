# 프로젝트 규칙 문서 생성 프롬프트

> 이 문서는 Figma 구현 규칙 문서(`doc/일반적인규칙.md`)를 **만들게 하는 프롬프트**입니다. Figma 디자인을 바로 코드로 구현하려면 [figma-guide.md](figma-guide.md)와 [figma-html.md](figma-html.md) 또는 [figma-html-css.md](figma-html-css.md)를 사용합니다. 아래 부록 A·B는 Figma 원문 번역이며, 구현 시 충돌하면 figma-guide.md가 우선합니다.

Figma MCP로 디자인을 가져와 이 저장소에 구현할 때 AI 어시스턴트가 따를 규칙 문서를 만들기 위한 프롬프트입니다.
Figma가 제공하는 원본 예시는 React 프로젝트를 전제로 하므로, 이 저장소(Gulp + SCSS + 정적 HTML) 구조에 맞게 질문을 바꿨습니다.

## 사용 방법

1. 아래 "프롬프트" 블록 전체를 AI 어시스턴트(Claude Code, Codex 등)에 붙여 넣습니다.
2. 결과는 `doc/일반적인규칙.md`에 새로 저장하도록 요청합니다.
3. 생성된 규칙을 직접 검토한 뒤, 필요하면 [AGENTS.md](../AGENTS.md)에서 링크합니다.
4. 함께 적용할 규칙은 이 문서의 부록을 참고합니다. 프롬프트도 AI가 이 부록을 읽도록 지시합니다.
   - [부록 A. Figma MCP 연동 규칙](#부록-a-figma-mcp-연동-규칙): MCP 호출 순서와 구현 원칙
   - [부록 B. 자산 관련 지침](#부록-b-자산-관련-지침): Figma MCP 자산 사용 규칙
   - [부록 C. Figma 파일 구조 최적화](#부록-c-figma-파일-구조-최적화): 디자인 파일 쪽 준비 사항

> 저장소 구조가 바뀌면 프롬프트의 경로와 명령도 함께 갱신합니다.

## 프롬프트

````markdown
이 저장소를 직접 읽고 분석해서, Figma MCP(Model Context Protocol)로 받은 디자인을 이 프로젝트에 구현할 때 따를 규칙 문서를 작성해 줘.
결과는 `doc/일반적인규칙.md`에 한국어 마크다운으로 저장해.

## 작성 원칙

- 추측하지 말고 실제 파일을 읽고 확인한 내용만 규칙으로 쓴다. 각 규칙에 근거 파일 경로를 적는다.
- 없는 기능(아이콘 시스템, 토큰 변환 도구, CDN 등)은 "없음"으로 적고, 임의로 만들어 넣지 않는다.
- 문서끼리 내용이 다르거나 코드와 문서가 다르면 규칙에 섞지 말고 "확인 필요" 항목으로 따로 모은다.
- 핵심 패턴은 이 저장소의 실제 코드를 짧게 인용한 스니펫으로 보여 준다.
- 분석만 하고 소스 파일(`src/`, `gulpfile.js`, 설정 파일)은 수정하지 않는다.

## 먼저 읽을 파일

- 작업·검증 지침: `AGENTS.md`
- 빌드: `package.json`, `gulpfile.js`, `doc/gulp.md`
- SCSS: `src/scss/style.scss`, `src/scss/abstracts/*`, `src/scss/base/*`, `src/scss/layout/_every-layout.scss`, `src/scss/components/*`, `src/scss/pages/*`, `src/scss/utilities/*`
- 스타일 규칙 문서: `doc/scss-guide.md`, `doc/layout-guide.md`, `doc/a11y-checklist.md`
- 마크업과 스크립트: `src/pages/index.html`, `src/js/main.js`
- Storybook: `.storybook/main.ts`, `.storybook/preview.js`, `src/stories/*`, `doc/storybook.md`
- Figma 관련 기존 규칙: `doc/figma-rules-prompt.md`의 부록 A~C, `doc/figma-guide.md`

## 분석할 항목

### 1. 디자인 토큰

- 색상, 글꼴, 글자 크기, 간격, 분기점이 각각 어디에 정의되어 있는가?
  (예: `src/scss/abstracts/_variables.scss`의 SCSS 변수, `src/scss/base/_base.scss`의 `--s0` 같은 CSS 사용자 정의 속성)
- SCSS 변수와 CSS 사용자 정의 속성 중 어떤 값을 언제 쓰는가?
- 토큰 이름 규칙은 무엇인가? (`doc/scss-guide.md`의 변수 규칙 포함)
- Figma 변수(색상·간격·서체)를 이 토큰에 어떻게 대응시킬지, 맞는 토큰이 없을 때 어디에 어떤 이름으로 추가할지 규칙을 제안한다.
- 토큰 변환 도구(Style Dictionary 등)가 있는가?

### 2. 레이아웃과 컴포넌트

- 이 프로젝트는 UI 프레임워크 컴포넌트가 아니라 HTML 마크업 + SCSS 클래스로 구성된다. 이 전제를 확인한다.
- `l-` 레이아웃 클래스(`l-stack`, `l-cluster`, `l-grid`, `l-switcher` 등)의 목록, `data-*` 변형 속성, 사용 목적을 정리한다.
- `c-` 컴포넌트와 `u-` 유틸리티, `is-`/`has-` 상태 클래스의 규칙과 BEM 형식을 정리한다.
- Figma의 Auto Layout(방향, gap, padding, 정렬, wrap)을 어떤 `l-` 클래스와 SCSS로 옮길지 대응표를 만든다.
- 반복 요소(버튼, 카드 등)를 새 컴포넌트 파셜로 만드는 기준과 파일 위치(`components/` 대 `pages/`)를 정리한다.
- Storybook 스토리는 어떻게 작성하고 CSS를 어떻게 불러오는가? Code Connect 설정이 있는가?

### 3. 프레임워크, 라이브러리, 빌드

- HTML/SCSS/JavaScript의 처리 방식과 사용 라이브러리(jQuery 버전 포함)를 정리한다.
- Gulp 작업(`build`, `dev`, `prettier`)이 하는 일, 원본(`src`)과 생성 결과(`dist`)의 관계를 정리한다.
- HTML include(`@@include`) 설정을 확인한다. `gulpfile.js`는 `src/partials`를 감시하지만 폴더가 없을 수 있으므로 실제 존재 여부를 확인하고, 공통 마크업을 나눌 때의 규칙을 제안한다.
- `npm test`처럼 실제 검사가 아닌 명령이 있으면 명시한다.

### 4. 자산 관리

- 이미지·폰트·파비콘은 어디에 두고 HTML·SCSS에서 어떤 상대 경로로 참조하는가? (`dist` 기준 경로 포함)
- 빌드 시 어떤 자산이 복사되고, 이미지 최적화나 CDN 설정이 있는가?
- Figma MCP가 localhost 자산 URL을 줄 때 파일을 내려받아 어느 폴더에 어떤 이름 규칙으로 저장할지 정한다.
- 정보 이미지와 장식 이미지의 `alt` 처리 규칙을 정한다.

### 5. 아이콘

- 아이콘 저장 위치, 사용 방식(inline SVG, `<img>`, 배경 이미지), 이름 규칙이 있는가?
- 아이콘 패키지를 새로 설치하지 않는다는 부록 B(자산 관련 지침)와 어떻게 맞출지 정리한다.
- 접근 가능한 이름이 이미 있는 버튼 안의 아이콘은 `aria-hidden` 처리 등 중복 읽기 방지 규칙을 정리한다.

### 6. 스타일 작성 방식

- 진입점 `style.scss`의 `@use` 순서와 새 파셜 추가 방법을 정리한다.
- 파셜에서 `@use '../abstracts' as *;`만 불러오는 규칙, 중첩 깊이, 선택자, 선언 순서를 정리한다.
- 모바일 우선 반응형과 `mq()` 믹스인 사용법, `$breakpoints` 값을 정리한다.
- `font-style()`, `container()` 등 기존 믹스인의 사용법과 쓸 상황을 정리한다.
- `rem`/`px` 사용 기준을 확인한다.

### 7. 프로젝트 구조

- `src/` 폴더 구조를 트리로 보여 주고 각 폴더의 역할을 적는다.
- 새 챌린지를 시작할 때 바꿔야 하는 값(분기점, 폰트, 색상, 페이지 제목 등)을 정리한다.

## Figma MCP 결과를 이 프로젝트로 옮기는 규칙

다음 내용을 반드시 포함한다.

- Figma MCP 출력(보통 React + Tailwind)은 디자인과 동작을 설명하는 참고 자료일 뿐 최종 코드가 아니다.
- JSX는 시맨틱 HTML로, Tailwind 클래스는 `l-`/`c-`/`u-` 클래스와 SCSS 토큰으로 바꾼다. 대응표를 예시와 함께 제시한다.
- 절대 위치·고정 너비는 Every Layout 패턴과 유연한 크기로 바꾸고, 바꿀 수 없을 때만 예외로 남긴다.
- 상호작용이 필요하면 `src/js/main.js`의 기존 방식을 따르고 상태는 `is-` 클래스와 ARIA 속성으로 표현한다.
- 수정은 `src/`에서만 하고 `dist/`는 직접 수정하지 않는다.
- 구현 후 부록 A(Figma MCP 연동 규칙)의 절차대로 Figma 스크린샷과 비교하고, `AGENTS.md`의 검증 원칙(분기점 직전·직후, hover·focus, 접근성)을 적용한다.

## 결과 문서 형식

1. 요약: 이 프로젝트의 기술 구성 5줄 이내
2. 위 7개 항목별 규칙 (근거 파일 경로와 코드 스니펫 포함)
3. Figma → 코드 변환 대응표 (Auto Layout, 색상·간격·글꼴 변수, 컴포넌트, 자산)
4. 구현 체크리스트 (MCP 호출 순서부터 검증까지)
5. 확인 필요 항목: 문서와 코드가 다르거나 현재 비어 있는 부분
````

## 부록 A. Figma MCP 연동 규칙

이 규칙은 Figma 입력을 이 프로젝트의 코드로 옮기는 방법을 정의하며, Figma 기반의 모든 변경에서 반드시 따라야 한다.

### 필수 절차 (생략하지 않는다)

1. 먼저 get_design_context를 실행해 정확한 노드의 구조화된 표현을 가져온다.
2. 응답이 너무 크거나 잘리면 get_metadata를 실행해 상위 수준의 노드 맵을 얻은 뒤, 필요한 노드만 get_design_context로 다시 가져온다.
3. get_screenshot을 실행해 구현할 노드 변형(variant)의 시각적 참고 이미지를 얻는다.
4. get_design_context와 get_screenshot 결과를 모두 확보한 뒤에만 필요한 자산을 내려받고 구현을 시작한다.
5. 출력(보통 React + Tailwind)을 이 프로젝트의 규칙, 스타일, 프레임워크로 옮긴다. 가능한 한 프로젝트의 색상 토큰, 컴포넌트, 타이포그래피를 재사용한다.
6. 완료로 표시하기 전에 Figma와 비교해 모양과 동작이 1:1로 일치하는지 검증한다.

### 구현 규칙

- Figma MCP 출력(React + Tailwind)은 디자인과 동작을 표현한 자료로 다루며, 최종 코드 스타일로 보지 않는다.
- 해당되는 경우 Tailwind 유틸리티 클래스를 프로젝트에서 선호하는 유틸리티나 디자인 시스템 토큰으로 바꾼다.
- 기능을 중복해서 만들지 말고 기존 컴포넌트(예: 버튼, 입력 필드, 타이포그래피, 아이콘 래퍼)를 재사용한다.
- 프로젝트의 색상 체계, 타이포그래피 스케일, 간격 토큰을 일관되게 사용한다.
- 저장소에서 이미 채택한 라우팅, 상태 관리, 데이터 요청 패턴을 따른다.
- Figma 디자인과 시각적으로 1:1 일치하도록 노력한다. 충돌이 생기면 디자인 시스템 토큰을 우선하고, 화면과 맞추기 위한 간격이나 크기 조정은 최소한으로 한다.
- 최종 UI를 Figma 스크린샷과 비교해 모양과 동작을 모두 검증한다.

## 부록 B. 자산 관련 지침

규칙 파일(예: `.cursor/rules`)로 따로 쓸 때는 아래 frontmatter를 함께 둔다.

```markdown
---
description: Figma MCP 서버 규칙
globs:
alwaysApply: true
---
```

- Figma MCP 서버는 이미지와 SVG 자산을 제공하는 자산 엔드포인트를 제공한다.
- 중요: Figma MCP 서버가 이미지나 SVG의 소스로 localhost 주소를 반환하면 그 이미지나 SVG 소스를 그대로 사용한다.
- 중요: 새 아이콘 패키지를 import하거나 추가하지 않는다. 모든 자산은 Figma 응답(payload)에 포함되어 있어야 한다.
- 중요: localhost 소스가 제공되면 placeholder를 사용하거나 새로 만들지 않는다.

## 부록 C. Figma 파일 구조 최적화

설계 의도를 가장 잘 이해할 수 있도록 Figma 파일에 맥락을 담는 방법이다. 이렇게 하면 MCP와 AI 어시스턴트가 명확하고 일관성 있으며 시스템과 잘 맞는 코드를 생성할 수 있다.

### 컴포넌트를 사용한다

버튼, 카드, 입력 필드, 내비게이션 항목 등 반복되는 모든 요소는 컴포넌트로 만든다. 재사용이 가능해지고(특히 Code Connect와 함께 사용할 때) 파일도 더 깔끔하게 유지할 수 있다.

### Code Connect로 컴포넌트를 실제 코드에 연결한다

코드에서 컴포넌트 재사용을 일관되게 유지하는 가장 확실한 방법이다. 이 연결이 없으면 모델은 추측에 의존하게 된다.

### 토큰에 Figma 변수를 사용한다

간격, 색상, 모서리 반경(radius), 서체에 변수를 적용한다.

### 레이어와 컴포넌트에 의미 있는 이름을 쓴다

`Frame1268`, `Group5` 같은 기본 이름을 `CardContainer`, `ProductImage`, `CTA_Button`처럼 의도가 드러나는 이름으로 바꾼다. 모델이 어떤 데이터를 다루는지, 어떤 기능을 가져야 하는지 더 잘 이해할 수 있다.

### 자동 레이아웃(Auto Layout)을 사용한다

자동 레이아웃을 사용하면 디자인의 반응성을 높이고 레이아웃 의도를 명확하게 전달할 수 있다. 절대 위치 지정을 피할 수 있어 일반적으로 더 깔끔하고 예측 가능한 코드가 나온다.

팁: 코드를 생성하기 전에 Figma에서 프레임 크기를 조정해 예상대로 동작하는지 확인한다.

### 주석을 사용한다

요소가 어떻게 동작하고, 정렬되고, 반응해야 하는지처럼 시각 요소만으로는 파악하기 어려운 디자인 의도를 전달할 수 있다.

### 개발 리소스를 사용한다

개발 모드(Dev Mode)에서 레이어에 연결된 개발자 리소스 링크를 가져온다.
